# 破解改动分析：`Plain Craft Launcher 2测试版破解全部主题+移除更新.exe`

> 样本 SHA-256：`a8df67afa886acf3cf6325602d4472703bdc955b756e514eed4faece3903b7f7`
> 对照物：① 官方开源仓库 `Meloong-Git/PCL` tag `2.14.0.0`（VB 源码）② 官方 2.13.1.1 正式版二进制（含真实 ModSecret 实现）
> 文件名宣称的两项改动（破解全部主题 / 移除更新）**均已证实**，并额外发现第 3、4 处配套改动。

---

## 1. 结论速览

| # | 位置 | 改动 | 直接效果 |
|---|---|---|---|
| 1 | `ModSecret.ThemeCheckOne(int Id)` | 方法体被替换为 `return true;` | 全部 15 个主题（含 5 个隐藏主题 + 自定义主题）无条件解锁 |
| 2 | `ModSecret.UpdateCheckByButton()` | 方法体被替换为一段破解者留言弹窗 | 点「检查更新」不再检查，弹出一段嘲讽文字 |
| 3 | `ModSecret.UpdateStart(bool Silent, IEnumerable<string> UrlsOverride)` | 方法体被清空（`ret`） | 即使有代码路径调用，也永远不会下载更新 |
| 4 | `ModSecret.ServerSub(...)` 公告动作分支 `"update"` / `"slientupdate"` | 分支体被清空为 `break;` | 服务端公告无法再触发更新（第 3 条的配套补丁） |

**没有被改动的部分**（重要，说明这是"外科手术式"补丁而不是重新编译的魔改版）：
赞助码 ECDSA 校验、识别码生成、`CurrentRank`、`HasUpdatePermission`、`ServerSub` 的公告/配置下载、
`IsLauncherNewest()`、`UpdateRestart()`、`UpdateReplace()`、`DownloadLatestPCL()`、主题调色板与 `ThemeRefresh` 全套逻辑，全部保留原样。

## 2. 取证方法

1. **全量反编译**：ILSpy 8.2 → 164 个 C# 文件（3.27 MB），逐行可读
2. **退化方法体扫描**：对全部 6336 个 `MethodDef` 做「方法体 ≤ 3 行且为 `return true/false/null/0` 或空」的模式扫描，
   在 5996 个有 IL 的方法中筛出 23 个候选，逐一与官方源码比对 → 精确定位 3 处异常
3. **官方源码对照**：`Meloong-Git/PCL` tag `2.14.0.0`（开源版，`ModSecret` 被作者删改过）+ 官方 **2.13.1.1 正式版二进制**
   （含**未被删改的真实 `ModSecret` 实现**，可直接读出"原始代码长什么样"）
4. **二进制取证**：方法 RVA/IL 尺寸、方法体折叠、RVA 单调性、文件尺寸差
5. **活体验证**：复原 CDN 签名算法（`MD5(path-ts-rand-0-PCL2Server)`）并成功拉取 `ServerConfig.json`，
   确认官方更新/快照通道结构

## 3. 改动 1 —— 主题全解锁

### 3.1 官方原始实现（从 2.13.1.1 官方二进制还原，`ModSecret.vb`）

```vb
Friend Function ThemeCheckOne(Id As Integer) As Boolean
    If {0, 1, 2, 3, 4, 42}.Contains(Id) Then Return True          ' 免费主题 + 特殊主题 42
    If PotatoFeatures.Contains("Theme" & Id) Then Return True      ' 赞助码携带的主题特征
    Select Case Id
        Case 8
            Return CurrentRank >= 23                               ' 秋仪金：赞助等级 ≥ 23
        Case 14
            Return Enumerable.Range(5, 9).Count(AddressOf ThemeCheckOne) >= 5  ' 自定义主题：需先解锁 5 个隐藏主题
        Case Else
            If Settings.Get(Of String)("UiLauncherThemeHide").Contains("7") Then ThemeUnlock(7, False)
            Return Settings.Get(Of String)("UiLauncherThemeHide2").Split("|").Contains(Id.ToString())
    End Select
End Function
```

即：`0..4` 与 `42` 免费；`5..14` 必须分别满足「赞助特征 / 赞助等级 23 / 集齐 5 个隐藏主题 / 在解锁列表 `UiLauncherThemeHide2` 中」。

### 3.2 破解版实际代码（`源码/CSharp反编译/PCL/ModSecret.cs:843`）

```csharp
internal static bool ThemeCheckOne(int Id)
{
	return true;
}
```

- IL 体只有 **2 字节**（`ldc.i4.1` + `ret`），参数 `Id` 完全未使用
- 方法 RVA `0x0005BBF`，IL 大小 2

### 3.3 效果

`ThemeCheckAll` / `ThemeRefresh` / `ServerRequirement("unlockedtheme =")` / 启动日志全部依赖此函数，于是：

- `0..14` 与 `42` 全部 `ThemeCheckOne → true`
- 设置页里 5 个隐藏主题的「未解锁」遮罩、锁图标、提示文字全部按"已解锁"渲染
  （`LabLauncherTheme5Unlock.Visibility = Collapsed`、`RadioLauncherTheme6..14.IsEnabled = true` 等分支全部命中）
- 秋仪金（8）、极客蓝（11）、自定义主题（14）不再需要赞助等级/解密游戏/前置条件
- 启动日志固定输出「已解锁反馈主题」（`Application.xaml.vb:211` 的 `ThemeCheckOne(9)`）
- 服务端公告的 `unlockedtheme =` 条件分支恒定命中

## 4. 改动 2 —— 「检查更新」被替换为破解者留言

### 4.1 官方原始实现（2.13.1.1 官方二进制）


## 5. 改动 3 —— 更新下载被清空

### 5.1 官方原始实现（2.13.1.1）

`UpdateStart` 是一个完整的更新流水线（约 120 行）：

```
IsUpdating 互斥 → 从 ServerConfig.Update.{Release|Snapshot} 取 DownloadUrls/PatchUrls
  → 生成 LoaderCombo("启动器更新") = [获取更新信息 → LoaderDownload("下载更新文件") → 安装更新]
  → 安装阶段：解压 zip 或应用 PA30 增量补丁
  → 完成后 IsUpdateWaitingRestart = true → UpdateRestart(TriggerRestartAndByEnd)
  → 拉起 "PCL\Plain Craft Launcher 2.exe --update <pid> <old> <new> <restart>"
```

其中 `UpdateMark`（本样本为 `"EmptyMark****…"`）决定走全量包还是增量补丁：
`StartsWithF(UpdateMark, "Empty")` 为真 → 使用 `PatchUrls`。

### 5.2 破解版实际代码（`源码/CSharp反编译/PCL/ModSecret.cs:883`）

```csharp
private static void UpdateStart(bool Silent, IEnumerable<string> UrlsOverride = null)
{
}
```

- IL 大小 **1 字节**（仅 `ret`）
- 与 `GeneratePotatoCode()` **共享同一方法体**（同为 RVA `0x0005A68`，说明编译器/重写器做了空方法体折叠）

### 5.3 残留物（说明是"就地掏空"而非"整段删除"）

破解版里仍然保留了大量更新相关符号，只是再也不会被执行：

| 符号 | 状态 |
|---|---|
| `_0024STATIC_0024UpdateStart_00240212151280E91E_0024IsSilentUpdate` | 静态局部变量仍在（VB 编译器为 `Static` 生成） |
| `IsUpdating`、`IsUpdateWaitingRestart`、`IsUpdateRestartWaitingTasks` | 字段仍在 |
| `UpdateMark` | 仍为 `"EmptyMark****…"`（400 个 `*`，官方原值，非破解者改动） |
| `HasUpdatePermission` | 仍实现（`CurrentRank >= 12 || PotatoFeatures.Contains("Update")`） |
| `UpdateRestart` / `UpdateReplace` | **完整保留**（`--update` 参数、进程替换、失败提示文案都在） |
| `DownloadLatestPCL` | **完整保留**（整合包打包时仍会下载官方最新正式版到 `PathTemp\Latest.exe`） |

也就是说：**「下载更新」这条路被掐断，但「被外部 `--update` 参数调用时执行替换」这条路仍然可用。**

## 6. 改动 4 —— 服务端公告的更新动作被空转

官方 2.13.1.1 的 `ServerSub` 公告动作分支：

```csharp
case "update":
case "slientupdate":
{
    _ = (JObject)val4.Value;
    bool silent = Operators.CompareString(val4.Name, "slientupdate", TextCompare: false) == 0;
    if (!HasUpdatePermission)
    {
        if (!silent) InputPotatoCode(IsUpdating: true);
        if (!HasUpdatePermission) break;
    }
    UpdateStart(silent);
    break;
}
```

破解版（`源码/CSharp反编译/PCL/ModSecret.cs:1285`）：

```csharp
case "update":
	break;
case "slientupdate":
	break;
```

- 把「权限校验 + 弹土豆码 + 调 `UpdateStart`」整段删掉，只留 `break`
- 这是改动 3 的**配套**：即使服务端公告下发 `update` 动作，也不会再触碰更新逻辑
- 其余公告动作（`copy` / `website` / `stop` / `setup`）**保持原样**，说明破解者只针对更新

## 7. 二进制层面证据

| 指标 | 破解版 2.14.0.0 | 官方 2.13.1.1 | 官方 2.14.0.0 快照（加密容器） |
|---|---:|---:|---:|
| 文件大小 | 5,985,792 B | 5,750,272 B | 5,985,280 B（密文） |
| MethodDef | 6336 | 6116 | — |
| 有 IL 的方法 | 5996 | 5777 | — |
| IL 总字节 | 629,869 | 612,448 | — |
| 共享方法体分组 / 涉及方法 | 156 / 709 | **0 / 0** | — |
| RVA 相对 token 顺序逆序数 | **1211** | **0** | — |
| 空方法折叠（同一 RVA） | 199 个方法共享 `0x21E1`（`ret`） | 无 | — |

### 7.1 解读

- 破解版与官方 2.14.0.0 快照的密文体积仅差 **512 字节**（正好一个 PE 对齐粒度），
  与「只改了 4 个方法体 + 重写器重新排版」的规模完全吻合
- 破解版出现 709 个**折叠方法体**与 1211 处 **RVA 非单调**，而官方 2.13.1.1 是 0 / 0（编译器顺序输出）。
  这说明该镜像**不是**由 MSBuild/VBC 直接产出的，而是经过一次**程序集重写**（IL 编辑器保存 / 保护器预处理）。
  官方 2.14 快照版本身以加密容器分发（`update/Snapshot.zip` 内不是有效 PE），也印证官方在这一代引入了额外保护/重写环节
- 被改方法本身的 IL 特征（`ThemeCheckOne` = 2 B、`UpdateStart` = 1 B、`UpdateCheckByButton` = 50 B）与
  「用 dnSpy/dnlib 类工具就地替换方法体」完全一致

### 7.2 判定

| 假设 | 支持证据 | 反对证据 |
|---|---|---|
| A. 官方 2.14.0.0 快照 exe + IL 就地补丁 | 体积差 512 B；4 处改动的 IL 都极短；其余 630 KB IL 原样保留 | 折叠方法体与 RVA 逆序无法由补丁工具解释，只能归因于官方自身的保护/重写流程 |
| B. 用完整 VB 源码重新编译 | `VersionBranchMain = "Official"`、真实 ECDSA 公钥、真实 OAuth ClientId 等「开源版没有」的内容齐全 | 若是源码重编译，方法布局应与官方一致（0 折叠、0 逆序），实际不符 |

**倾向 A**：样本 = 官方快照版二进制（本身已被官方重写/保护处理）+ 4 处方法体级补丁。
但无法 100% 排除「破解者拿到了完整本体源码并用同一套重写流水线重新构建」的可能。

## 9. 是否存在第 5 处更隐蔽的改动？

**结论：以当前证据看，除上述 4 处外未发现其它改动；但不能给出「绝对没有」的证明。**

已做的排查：

1. **退化方法体扫描**：全量 5996 个有 IL 的方法 → 23 个候选 → 逐个与官方源码对照，
   除 3 处外全部是构造器 / 转发 / 原本就为空的开发接口（`ModDevelop.Start`、`MyMsgLogin.Btn1_Click`、`GeneratePotatoCode`）
2. **字符串扫描**：全文件检索破解者自述、常见破解标记（`破解`、`授权`、`仅供学习`、`移除更新`），
   仅命中 1 处（第 4.2 节留言），未发现隐藏后门、外联地址或二次校验绕过
3. **网络地址全量提取**：从源码抽出全部 160+ 个 URL，逐条核对均为官方域名
   （Mojang / BMCLAPI / Modrinth / CurseForge / 腾讯云 COS / GitHub），**没有新增可疑域名**
4. **敏感常量核对**：`OAuthClientId`、`ClsBaseUrl`、`EcdsaPublicKey`、CurseForge API Key（Base64）
   与官方一致，未被替换为破解者自己的凭据

无法排除的原因：官方 2.14.0.0 快照二进制以加密容器分发，无法做逐字节/逐方法比对。
若需彻底确认，验证方法见下节。

### 验证方法（可复现）

1. 从任意一台运行过官方 2.14.0.0 快照版的机器上，取 `%TEMP%\PCL\` 或安装目录下**已解密落盘**的
   `Plain Craft Launcher 2.exe`（官方更新流程会把解密后的 exe 写到磁盘）
2. 用本仓库 `证据/方法布局-破解版.csv` 的同一工具（`tools/MetaDump`）对两个 exe 各导出一份方法布局
3. `ilspycmd -p -o <dir>` 分别反编译两份，`git diff --no-index` 即可得到**完整、逐方法的改动清单**
   （同版本、同编译器、同反编译器 → 差异噪声接近 0）

## 10. 一句话总结

> 这不是"魔改版"，而是**官方 2.14.0.0 快照版**上做了 4 处精准手术：
> 把主题判定函数改成恒真（全主题解锁）、把更新检查换成一段留言、把更新下载函数掏空、
> 并把服务端公告的更新动作一起空转。除更新与主题外，登录、下载、启动、赞助码、崩溃分析等全部功能完好。
